# Практика №16 Интеграционные тесты Notes API

Самостоятельный модуль: HTTP на chi → handler → service → repository (`database/sql`, pgx) → PostgreSQL 16.6. Выбран вариант A — Docker Compose. Практики №11–12 не изменяются.

## Одна команда в PowerShell

Запустите Docker Desktop с Linux Engine, затем из **любого каталога** Windows PowerShell 5.1 или PowerShell 7:

```powershell
& 'D:\MAG\GO\practic\practices\pz16-integration\run-local.ps1'
```

Скрипт подключает `setup.ps1`, проверяет Engine, создаёт уникальный проект `pz16-<UUID>` с собственным томом. Пароль генерируется в памяти, ручной ввод не нужен. Docker назначает свободный порт `127.0.0.1::5432`. После healthcheck скрипт передаёт временный DSN только через окружение процесса, запускает тесты и проверки, сохраняет компактные логи в `reports/logs/pz16/`. В `finally` выполняет `down --volumes` только для своего проекта, проверяет отсутствие его контейнеров и томов, восстанавливает окружение и исходный каталог. Локальный PostgreSQL и чужие контейнеры не используются. При первом запуске нужен доступ к Docker registry и Go proxy.

Скрипт выполняет:

```powershell
go test -count=1 -timeout=120s ./...
go test -count=1 -timeout=120s -v ./integration/...
go test -count=2 -shuffle=on -timeout=120s ./integration/...
go fmt ./...
go vet ./...
go build ./...
go mod verify
```

`-count=1` отключает кеш результатов. Отсутствующий DSN или маркер проекта вызывает **FAIL**, а не SKIP. Указанные команды тестов без скрипта намеренно не проходят без тестовой БД. Скрипт запускает настоящий API через `httptest.NewServer` внутри тестов; отдельный фоновый exe не нужен. `cmd/api` также собирается; ручной сервер слушает loopback, по умолчанию порт 0.

## Контракт

| Метод и путь | Ответ |
| --- | --- |
| POST /api/v1/notes | 201 Note, Location |
| GET /api/v1/notes | 200 массив Note, пустой список `[]`, порядок ID |
| GET /api/v1/notes/{id} | 200 Note; 400 неверный ID; 404 отсутствующий |
| PATCH /api/v1/notes/{id} | 200 Note; 400 неверные поля/ID; 404 отсутствующий |
| DELETE /api/v1/notes/{id} | 204 без тела; 400 неверный ID; 404 отсутствующий |

Note содержит `id`, `title`, `content`, `createdAt`, `updatedAt`. POST требует непустой после TrimSpace заголовок. PATCH принимает хотя бы одно ненулевое поле, сохраняет отсутствующие поля, допускает пустой content. Неизвестные поля, неверный Content-Type, лишний JSON и тело больше 1 МиБ дают 400. JSON-ответы имеют `application/json; charset=utf-8`. Ошибки — `{"error":"invalid request"}`, `{"error":"note not found"}` или безопасный общий 500. Пагинация и фильтр в текущий контракт не входят.

## Изоляция и миграция

Каждый из восьми интеграционных тестов создаёт случайную схему `it_<token>` внутри одноразовой `notes_test`, устанавливает `search_path` всем подключениям своего пула и использует реальные HTTP-запросы. Фикстуры создаются через POST. `t.Cleanup` закрывает сервер/пул и удаляет только собственную схему. Никаких DROP/TRUNCATE общих таблиц. Порядок тестов проверяется повторным прогоном с shuffle.

Встраиваемая миграция `internal/db/migrate.sql` создаёт notes с PK, NOT NULL и CHECK заголовка, временными метками TIMESTAMPTZ. Повторная миграция сохраняет данные. `updated_at` обновляется атомарно SQL-операцией UPDATE через `clock_timestamp()`, триггер не требуется. Запросы параметризованы, контекст запроса передаётся до БД; SQL-операции ограничены 3 секундами, HTTP-клиент — 5 секундами.
