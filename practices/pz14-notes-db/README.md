# Практика №14 — PostgreSQL и оптимизация Notes API

Самостоятельный модуль на основе поведения Notes API №11. Использует chi, database/sql и pgx/v5 v5.7.2. Практики №11–12 не изменяются. Реальные соединения задаются переменными PG*; пароль и DSN не записываются в код или логи.

## Одна команда в Windows PowerShell

Из любого каталога:

```powershell
& 'D:\MAG\GO\practic\practices\pz14-notes-db\run-local.ps1'
```

Нужны локальный PostgreSQL на 127.0.0.1:5432, psql.exe и пароль роли postgres. При другой роли заранее задайте `$env:PGUSER`. Скрипт подключает setup.ps1, собирает свои exe, один раз запрашивает пароль через Read-Host -AsSecureString и создаёт учебную БД pz14_notes только при отсутствии. Пароль передаётся процессам в PGPASSWORD, не в аргументах команд. В finally переменные PG* восстанавливаются, память SecureString/BSTR освобождается, собственные API и временные файлы убираются. Ни PostgreSQL-сервис, ни другие процессы не останавливаются.

Каждый запуск создаёт две новые схемы `pz14_<случайный UUID>_base` и `pz14_<тот же UUID>_opt`, по 100000 одинаковых детерминированных заметок. Существующие схемы, данные и индексы не удаляются. Baseline имеет только первичный ключ. Optimized дополнительно получает `(created_at DESC,id DESC)` и GIN для `to_tsvector('simple',title)`. Такой способ сохраняет честный baseline при повторном запуске. Учебные схемы остаются для проверки; каждый повтор потребляет дополнительное место. Бинарные файлы не остаются.

Скрипт проверяет одинаковые 50 строк OFFSET/keyset на логической глубине 80000, 300 последовательных строк keyset без пропусков/дубликатов, одинаковые результаты 20 одиночных запросов и одного батча, commit двух заметок вместе с audit и rollback после вставки первой заметки при ошибке второй. HTTP-сценарий проверяет CRUD, 400/404, JSON и DELETE 204 без тела.

Нагрузка: для каждой из четырёх комбинаций baseline/optimized × пул 1/8 измеряются list, get и batch. Каждый сценарий имеет 10 последовательных warmup-запросов и 200 измеряемых запросов с concurrency=8, без искусственных пауз. Это ограниченный closed-loop тест, не проверка производственной мощности. Ответы проверяются по ID и порядку. Логи содержат elapsed, RPS, p95/p99, ошибки и дельты ожидания пула. Все API используют свободный loopback-порт, выбранный самой ОС.

Небольшие логи сохраняются по умолчанию вне Git в `D:\MAG\GO\.local\pz14-results\<UUID>`; конечный путь печатается. Можно задать абсолютный каталог:

```powershell
& 'D:\MAG\GO\practic\practices\pz14-notes-db\run-local.ps1' -OutputDirectory 'D:\MAG\GO\.local\pz14-results-manual'
```

Повторный запуск с новым каталогом удобнее для сравнения. Не передавайте пароль в OutputDirectory или командной строке.

## API и пул

| Маршрут | Результат |
| --- | --- |
| POST /api/v1/notes | 201 Note + Location, транзакция note/audit |
| GET /api/v1/notes | 200 массив, limit 1..100, offset 0..100000 |
| GET /api/v1/notes/{id} | 200 Note; 404 при отсутствии |
| PATCH /api/v1/notes/{id} | 200 Note с updatedAt |
| DELETE /api/v1/notes/{id} | 204 без тела |
| GET /api/v1/notes/batch?ids=1,2,3 | максимум 20 уникальных ID, порядок сохранён |
| POST /api/v1/notes/many | массив 1..20 заметок, единая транзакция |
| GET /stats | database/sql DBStats |

В optimized keyset принимает парные `before_time` (RFC3339Nano) и `before_id`, требует offset=0. Порядок — created_at DESC,id DESC; условие `(created_at,id)<($1,$2)` соответствует индексу. В baseline keyset не рекламируется и возвращает 400. Baseline batch делает N запросов; optimized выполняет один ANY($1::bigint[]) с восстановлением порядка. GET по одному ID использует prepared statement в обоих вариантах и служит контрольным маршрутом.

Пример: первая страница `GET /api/v1/notes?limit=50`; следующая — тот же URL с before_time/before_id последней записи. Изменение набора во время просмотра не даёт snapshot-гарантии; проверка прогонов проводится на неизменной выборке.

Пул: MaxOpenConns=MaxIdleConns=1 или 8, ConnMaxLifetime=30 минут, ConnMaxIdleTime=5 минут, request context timeout=10 секунд. Пул 1 намеренно выявляет очередь при concurrency=8; пул 8 соответствует числу клиентов эксперимента. Выбор рабочего значения делается только по реальным метрикам, с учётом лимита соединений PostgreSQL. Подготовлены INSERT и SELECT по ID. Транзакция ReadCommitted атомарно сохраняет заметки и аудит; ошибки не оставляют частичные вставки (последовательности ID при rollback могут иметь пропуски).

## SQL и диагностика

`cmd/lab` выводит EXPLAIN (ANALYZE, BUFFERS) для OFFSET, keyset, полнотекстового поиска и одиночного/батч-запроса. GIN используется только с `to_tsvector('simple',title) @@ plainto_tsquery('simple',$1)`, не с LIKE. Индексы не удаляются ради baseline: он изолирован в собственной схеме.

pg_stat_statements используется, если он уже указан в shared_preload_libraries. Тогда расширение создаётся только в учебной БД и читаются актуальные calls/total_exec_time/mean_exec_time/rows. При отсутствии preload выводится причина, глобальная конфигурация и сервис не меняются. Доступные источники диагностики — EXPLAIN и метрики приложения.
