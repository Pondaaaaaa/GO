# Практика №13 — профилирование Go-приложения

Источник: `D:\MAG\GO\Текущий контроль\Практическое занятие №13.docx`. Задание допускает отдельный стенд `pprof-lab`; создать самостоятельный Go-модуль `practices/pz13-pprof/`. Соседние практики не менять. Внешняя БД и Docker не нужны.

## Обязательный результат

- Мини-сервер с `/work` и доступным только на loopback `/debug/pprof/`; демонстрационная тяжёлая функция — рекурсивный `Fib`, оптимизация — итеративный `FibFast`. Для `net/http/pprof` учесть, что импорт регистрирует обработчики в `http.DefaultServeMux`: при собственном mux маршруты нужно подключить явно либо использовать отдельный локальный сервер. Не оставлять профилировщик доступным извне.
- Получить реальные CPU-профиль **до** оптимизации, его `top`, `list Fib` и граф вызовов (`web`, `-svg` либо UI). После оптимизации повторить профиль с сопоставимыми входом и нагрузкой. Получить Heap-профиль, указать, что в нём измерялось (`inuse_space` или `alloc_space`), и сделать осторожный вывод по фактическим данным. При необходимости для осмысленного Heap-профиля добавить контролируемую аллоцирующую работу и описать её отдельно от Fib.
- Добавить ручной таймер `TimeIt`, зафиксировать реальные логи. Добавить корректные `testing.B` бенчмарки `Fib` и `FibFast`, проверить одинаковые входы и результаты. Выполнить `go test -bench=. -benchmem ./...` до/после и записать `ns/op`, `B/op`, `allocs/op`. Убедиться, что компилятор не удаляет вычисление как неиспользуемое. Сравнивать при одинаковых условиях; помнить о разбросе измерений.
- Собрать исполняемый файл с подходящими символами для `go tool pprof`; записать точные команды, версии Go, конфигурацию нагрузки и длительность. Выбрать свободные локальные порты вместо фиксированных 8080/9999, ограничить число запросов и время, очистить только собственные процессы. Желателен один `run-local.ps1` для воспроизводимого запуска, нагрузки, сбора и анализа; профили и прочие большие/временные артефакты не добавлять в Git без необходимости.
- Дополнительно: профили block/mutex, flame graph в UI, сравнительный график, автоматизация. Это бонусы; отсутствие block/mutex не считать провалом обязательной части.

## Отчёты и проверка

Проверить `go fmt`, `go vet`, `go test`, `go build`, работу `/work` и `/debug/pprof/`, реальные команды `go tool pprof`. Сохранить уместные небольшие текстовые логи в `reports/logs/` и настоящие снимки экрана в `reports/images/pz13/`, если они требуются для графа/UI. Не подменять граф выдуманной картинкой; если Graphviz или захват экрана отсутствует, выяснить конкретный блокер и честно отметить его.

`reports/pz13.md` и `reports/word/pz13.docx` по `context/REPORTS.md`: цель, структура и окружение; реальные CPU top/list/graph до и после, Heap-анализ, логи таймеров, результаты бенчмарков, что именно оптимизировано, таблица `ns/op`, `B/op`, `allocs/op` и аккуратный вывод. Ответить на **7 контрольных вопросов** исходного DOCX. Word создавать из завершённого Markdown штатным экспортёром, проверить совпадение содержания и наличие изображения.

В учебном DOCX пример `main.go` использует `fmt.Sprintf` без импорта `fmt`, а побочный импорт `net/http/pprof` сам по себе не подключает маршруты к новому `http.NewServeMux()`. Эти ошибки образца следует исправить в реализации, не копировать буквально.
