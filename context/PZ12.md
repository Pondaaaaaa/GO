# Практика №12 — документация Notes API

Источник: `D:\MAG\GO\Текущий контроль\Практическое занятие №12.docx`. Основа: завершённый `practices/pz11-notes/`. Создать **отдельный** Go-модуль `practices/pz12-notes/`, чтобы №11 продолжала запускаться самостоятельно. Предписанный практической частью путь — code-first: аннотации Go → `swaggo/swag` → сгенерированный пакет `docs/` → Swagger UI на `GET /docs/index.html`. Schema-first с `oapi-codegen` приведён как альтернатива, выполнять оба подхода не требуется.

## Что должно работать

- Сохранить все пять реальных операций из №11: `GET/POST /api/v1/notes`, `GET/PATCH/DELETE /api/v1/notes/{id}` и их фактические схемы/коды. Аннотировать все пять, добавить DTO `NoteCreate` и `NoteUpdate`, примеры моделей и ошибки `400/404/500` там, где применимо. `DELETE 204` — без тела.
- Общие аннотации `title`, `version`, `description`, `BasePath /api/v1` в `cmd/api/main.go`. Не переносить из учебного примера контакт или принадлежность вузу.
- Сгенерировать `docs/docs.go`, `docs/swagger.json`, `docs/swagger.yaml`; не редактировать их вручную. Подключить Swagger UI по `/docs/index.html`, проверить доступность страницы и самой спецификации, наличие всех пяти операций. Создать повторяемую команду/PowerShell-скрипт генерации и README.
- В исходном DOCX пример `ListNotes` упоминает `page`, `limit`, `q`, `X-Total-Count`, которых нет в №11; пример `PatchNote` не совпадает с названием `UpdateNote`. Не документировать несуществующее поведение: либо описать фактический API, либо реализовать и проверить расширение осознанно. Минимум для №12 — точное описание существующего CRUD.
- В №11 уже есть `api/openapi.yaml` формата **OpenAPI 3.0.3**. [Основной путь `swaggo/swag`](https://github.com/swaggo/swag) в его документации генерирует **Swagger 2.0**. Не выдавать `docs/swagger.yaml` за OpenAPI 3.0; указать разницу и назначение старого файла в README/отчёте. Ручную синхронизацию двух спецификаций не изображать как автоматическую.
