## Обязательная реализация

- Структура из задания: `main.go`, `internal/task/model.go`, `internal/task/repo.go`, `internal/task/handler.go`, `pkg/middleware/logger.go`, `pkg/middleware/cors.go`, `go.mod`, `go.sum`; добавь краткий README. Не создавай вложенный `.git`.
- Модель Task: `id` (`int64`), `title`, `done`, `created_at`, `updated_at`. In-memory хранилище с `sync.RWMutex`, возрастающим ID, методами `List/Get/Create/Update/Delete` и распознаваемой ошибкой `ErrNotFound`. Не отдавай наружу изменяемые указатели на записи без защиты блокировкой: операции чтения и обновления должны быть безопасны при параллельных запросах.
- Маршруты: `GET /health` → `200 OK`, текст `OK`; `GET /api/tasks` → `200` и JSON-список; `POST /api/tasks` → `201` и созданная задача; `GET /api/tasks/{id}` → `200` или `404`; `PUT /api/tasks/{id}` → `200` и обновлённая задача; `DELETE /api/tasks/{id}` → `204 No Content` без тела или `404`. Проверяй именно адреса без завершающего `/`, приведённые в задании.
- Для POST/PUT принимай JSON, проверяй ошибки декодирования и непустой `title` после обрезки пробелов. Неверное тело или ID → `400` с JSON-ошибкой; отсутствующий ID → `404` с JSON-ошибкой. Общий helper возвращает правильный `Content-Type` и статус. У `204` нет JSON-тела.
- Подключи через `chi` middleware логирования метода, пути и длительности, а также CORS: `Access-Control-Allow-Origin: *`, разрешённые GET/POST/PUT/DELETE/OPTIONS и нужные заголовки; preflight OPTIONS должен возвращать корректный статус и CORS-заголовки. В примере DOCX также подключены `chi` RequestID и Recoverer.
- По примеру порт `8080`, но он занят внешним `httpd`; сделай локальную настройку порта (например, `PORT`, по умолчанию `8080`) и проверяй на свободном порту без остановки стороннего процесса. Для PowerShell используй `curl.exe` и однострочные команды либо переносы с обратной кавычкой; символ `^` из примера DOCX относится к `cmd.exe`.

## Проверка и отчёт

Запусти `go fmt ./...`, `go vet ./...`, `go test ./...`, `go build ./...`, `go run .` и реальные HTTP-запросы ко всем маршрутам. Отдельно проверь создание → список → получение → обновление → удаление → `404` после удаления, неверный ID и JSON, `OPTIONS` и заголовки CORS. В отчёт вноси только фактические результаты.

Отчёт `reports/pz04.md` по `context/REPORTS.md` и DOCX: тема, дата, цели, дерево проекта, короткие фрагменты роутера/middleware/обработчиков, примеры запросов и ответов, объяснение ошибок и статусов, таблица «маршрут → запрос → ожидаемый/фактический ответ», выводы и ссылка на код. Ответь кратко на пять контрольных вопросов: ServeMux и chi; GET/POST/PUT/PATCH/DELETE; middleware; JSON-ошибки и статусы; хранение в памяти против БД. DOCX допускает **скриншоты или вставки JSON-ответов**; настоящие текстовые выводы достаточны. В DOCX также указаны ФИО и группа: не выдумывай их и не публикуй персональные данные в открытом репозитории; оставь поля для заполнения в личной копии отчёта.
