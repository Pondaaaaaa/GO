Читай `context/REPORTS.md` и `context/AUTOMATION.md`.

## Требуемая работа

- Создай `cmd/server/main.go`, `internal/cache/cache.go`, `go.mod`, `go.sum` и README. Используй `github.com/redis/go-redis/v9` и стандартный `net/http`. Клиент Redis получает адрес из конфигурации, поддерживает `Set(key, value, ttl)`, `Get(key)` и `TTL(key)`; закрывай клиент при завершении. Пример из задания использует TTL **10 секунд**.
- Реализуй `GET /set?key=...&value=...`, `GET /get?key=...` и `GET /ttl?key=...` по образцу DOCX. Валидируй пустые параметры, корректно различай отсутствие ключа (`redis.Nil`) и недоступность Redis; не выдавай сбой Redis как `404`. Ограничь время операций, чтобы запросы не зависали. Не выводи секреты в ответы или логи. Порт сервера должен настраиваться: `8080` на машине может быть занят.
- Проверь реальный сценарий: `/set` сохраняет значение с TTL 10 секунд; `/get` до истечения возвращает его; `/ttl` показывает положительное оставшееся время; после истечения `/get` возвращает отсутствие ключа. Для проверки TTL учитывай погрешность и задержку между запросами, не требуй ровно 10 секунд. Желательно подтвердить состояние также через `redis-cli` внутри своего контейнера.
- Задание называет это простым кэшем; отдельное подключение к PostgreSQL или новая предметная модель здесь не требуются. В отчёте объясни, как временное хранение результатов может уменьшать обращения к основной БД, не утверждая непроверенное ускорение.

## Автоматический запуск

Добавь `run-local.ps1` по `context/AUTOMATION.md`, запускаемый одной командой из любой директории. Он должен проверить Docker Engine, запустить **свой** временный Redis-контейнер на свободном локальном порту, дождаться готовности, запустить Go API на другом свободном порту, выполнить проверки `/set`, `/get`, `/ttl` и истечения TTL, показать понятный вывод для настоящих снимков и очистить только созданные им процессы/контейнер. Не трогай чужой Redis и не требуй пароль PostgreSQL: он в №7 не нужен. Если Docker Engine недоступен из среды Codex, выполни независимые Go-проверки и дай пользователю точную одну команду для запуска на его компьютере; фактические ответы не выдумывай.

Проверь `go fmt ./...`, `go vet ./...`, `go test ./...`, `go build ./...` и реальный HTTP-сценарий, когда доступен Docker. Фиксируй фактические версии и результаты. Не создавай зависимости на случайно работающий чужой контейнер.
