# Практика №16 — интеграционное тестирование Notes API с Docker и PostgreSQL

Источник: `D:\MAG\GO\Текущий контроль\Практическое занятие №16.docx`. Это продолжение темы Notes API из №11–12; создать отдельный модуль `practices/pz16-integration/`, не меняя предыдущие практики. Следовать `AGENTS.md`, `context/REPORTS.md` и `context/AUTOMATION.md`.

## Выбранная инфраструктура

В исходном задании разрешены два альтернативных способа: A — Docker Compose, B — testcontainers-go. Для этого проекта выбрать **A, Docker Compose**: он уже установлен, а требование инфраструктуры выполняется одним способом. В репозитории нужны `compose.yaml` (или `docker-compose.yml`), исходники API, миграция, интеграционные тесты и README. Не требуется одновременно реализовывать B.

Поднимать только отдельный контейнер PostgreSQL 16 (версия примера из DOCX; допустимо совместимое закреплённое значение). Тестовую БД, пользователя и пароль создавать только для одноразового учебного контейнера. Не коммитить реальные секреты или DSN. Выделять уникальное имя Compose-проекта для запуска, не занимать фиксированный хост-порт, не трогать локальный PostgreSQL и чужие Docker-ресурсы. Скрипт `run-local.ps1` из любого каталога должен автоматически: подключить локальный Go; проверить Docker; подготовить временные параметры БД; поднять Compose и дождаться ready; передать DSN тестам без вывода секрета; выполнить проверки; записать небольшой подлинный лог; удалить **только свои** контейнеры и тома в `finally`. Пароль локального PostgreSQL не нужен.

## Обязательная реализация и проверки

- Связка реальных слоёв **HTTP-маршрут → handler → service → repository → PostgreSQL**, предпочтительно на уже знакомом Notes API. `database/sql` с драйвером PostgreSQL или GORM допустимы. HTTP-тесты используют `httptest` или локальный тестовый сервер и обращаются к реальной контейнерной БД.
- Идемпотентная миграция таблицы `notes` с первичным ключом, полями title/content/created_at/updated_at, нужными ограничениями и, если требуется моделью, триггером обновления времени. Запрет на разрушительные миграции чужих объектов. Начальные данные/фикстуры и очистка должны делать тесты независимыми от порядка и повторных запусков.
- Проверить минимум POST create: 201, JSON с ID и соответствующая строка в БД; GET существующей: 200 и содержимое; GET отсутствующей: 404. Критерии оценивания ожидают основные CRUD-маршруты и эффекты в БД: добавить list, PATCH/PUT update и DELETE, проверить их статус, JSON и реальные INSERT/UPDATE/DELETE. Добавить 400 для неверного JSON/ID/валидации. Проверять `Content-Type` там, где ожидается JSON.
- `go test ./...` и `go test -v ./integration/...` должны действительно выполнить интеграционные кейсы при поднятом Compose, без `SKIP`. Сохранить подлинный `docker compose ps` при запущенном контейнере и вывод тестов с названиями и длительностями, 2–3 конкретных примера успешных тестов. Также выполнить fmt/vet/build/mod verify и явно указать версии. Не объявлять завершение, если Docker/БД или тесты недоступны.
