# Практика №14 — оптимизация PostgreSQL и пул соединений

Источник: `D:\MAG\GO\Текущий контроль\Практическое занятие №14.docx`. Основа — Notes API из №11–12. Создать отдельный Go-модуль `practices/pz14-notes-db/`, сохранив №11 и №12 без изменений. На компьютере есть PostgreSQL 18 и Docker Desktop; достаточно локального PostgreSQL, Compose из документа — пример, не обязательный способ запуска. Следовать `context/AUTOMATION.md`: одна команда PowerShell, только скрытый ввод пароля PostgreSQL, отдельная учебная БД и отсутствие секретов в Git/логах.

## Обязательный результат

- Реальное Notes API с PostgreSQL, схемой `notes`, миграцией без удаления данных, драйвером `pgx`/`database/sql` либо `pgxpool`. Настроить пул конкретными измеренными значениями и показать его статистику/ожидание соединений. Добавить подготовленный параметризованный запрос и транзакцию для связанных операций. Объяснить, где они полезны.
- На достаточно большой и одинаковой выборке показать **исходные проблемные SQL-запросы** и реальные `EXPLAIN (ANALYZE, BUFFERS)` до изменений. Затем применить индекс, keyset-пагинацию и батчинг вместо N+1; проверить корректность результатов и повторить планы. Для поиска по заголовку выбрать семантически подходящий индекс: пример документа с `GIN(to_tsvector(...))` относится к полнотекстовому поиску, а не автоматически к `LIKE 'prefix%'`. Индекс `(created_at, id)` должен соответствовать фактическому `ORDER BY` и предикату keyset.
- Провести ограниченную нагрузку на список заметок и получение по id/батч как минимум для двух конфигураций пула и до/после SQL-оптимизации. Собрать фактические RPS, p95, p99 и долю/число ошибок, условия нагрузки, размер данных и наблюдения о пуле. Не обещать улучшение, если измерения его не показали; сравнить одинаковые запросы и данные. Первый и повторный запуск должны сохранять честный baseline: проиндексированная таблица не может служить «до» после повторного запуска. Выбрать и документировать безопасную изоляцию baseline и optimized без `DROP`/`TRUNCATE` неизвестных данных.
- `pg_stat_statements` проверить и использовать, если доступно. На PostgreSQL 18 запросы используют актуальные имена колонок вроде `total_exec_time`, `mean_exec_time`; учебные `total_time`, `mean_time` могут быть устаревшими. `CREATE EXTENSION` само по себе может быть недостаточно без `shared_preload_libraries` и перезапуска сервера. Не менять глобальную конфигурацию PostgreSQL молча; при недоступности указать причину и опираться на EXPLAIN и метрики приложения. Redis/кэш и read/write split — бонусы, не обязательны.
