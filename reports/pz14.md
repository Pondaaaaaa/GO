## План безопасного сравнения

Каждый запуск создаёт две новые схемы в учебной БД pz14_notes: pz14_<UUID>_base и pz14_<UUID>_opt. В каждой запланированы 100000 одинаковых детерминированных строк. В baseline только первичный ключ; optimized получает индексы сортировки и полнотекстового поиска. Старые схемы не удаляются и не изменяются. Повторный запуск не использует ранее проиндексированную таблицу как baseline. Никаких DROP/TRUNCATE в коде нет; новые схемы остаются для последующей инспекции и требуют места.

Индекс `(created_at DESC,id DESC)` соответствует порядку списка и предикату keyset. GIN построен по `to_tsvector('simple',title)` и применяется только к соответствующему полнотекстовому запросу, а не к LIKE-префиксу. В учебном примере DOCX эти назначения были смешаны; здесь они разделены.

## SQL и ещё не полученные планы

В реализации baseline использует:

```sql
SELECT id,title,content,created_at,updated_at
FROM notes
ORDER BY created_at DESC,id DESC
OFFSET $1 LIMIT $2;
```

Для сравнения выбраны offset=80000, limit=50. Optimized получает ту же логическую страницу через известный курсор:

```sql
SELECT id,title,content,created_at,updated_at
FROM notes
WHERE (created_at,id)<($1,$2)
ORDER BY created_at DESC,id DESC
LIMIT $3;
```

Фактические имена таблиц в программе квалифицированы отдельными схемами; здесь показан читаемый SQL-фрагмент. Для текста используется:

```sql
CREATE INDEX notes_title_fts ON notes
USING GIN(to_tsvector('simple',title));
SELECT id,title FROM notes
WHERE to_tsvector('simple',title) @@ plainto_tsquery('simple',$1);
```

Baseline batch делает 20 отдельных prepared SELECT по id. Optimized выполняет один `WHERE id=ANY($1::bigint[])`; array_position возвращает строки в порядке входных ID. Скрипт должен сравнить результаты обоих вариантов и 300 последовательных строк keyset без пропусков/дубликатов.

**EXPLAIN (ANALYZE, BUFFERS) до/после не запускался: нет аутентифицированного подключения.** Seq Scan/Index Scan, Execution Time и BUFFERS пока не получены. Скрипт снимет планы OFFSET/keyset, полнотекстового поиска и одиночного/батч-запроса перед нагрузкой и после неё.

## Пул и транзакции

Настройки реализации: MaxOpenConns=MaxIdleConns=1 или 8, ConnMaxLifetime=30 минут, ConnMaxIdleTime=5 минут. Значение 1 предназначено для выявления очереди при восьми клиентах, 8 — для сравнения с числом клиентов. Это экспериментальные настройки, **не измеренный выбор оптимального пула**. GET /stats выдаёт DBStats; нагрузчик рассчитывает дельты WaitCount/WaitDuration и фиксирует OpenConnections/Idle/InUse.

Подготовлены параметризованные INSERT и SELECT по ID. CreateMany в одной транзакции ReadCommitted сохраняет заметки вместе с audit-записями. Валидация каждого элемента выполняется внутри транзакции, поэтому ошибка второй заметки должна откатить первую вставку. defer Rollback покрывает ошибку; Commit выполняется только после всех вставок. Реальные commit/rollback ещё требуют запуска. Пропуски последовательности ID при rollback нормальны и не считаются оставшейся заметкой.

pg_stat_statements пока не проверено. Скрипт сначала прочитает shared_preload_libraries. Если preload отсутствует, укажет точную причину и не изменит глобальную конфигурацию. При доступности создаст расширение только в учебной БД и использует актуальные total_exec_time/mean_exec_time. До реального запуска доступность расширения утверждать нельзя.

## Контрольные вопросы

1. **Чем keyset лучше OFFSET/LIMIT на больших объёмах?** OFFSET требует пройти или отсортировать пропускаемые строки; стоимость растёт с глубиной. Keyset с подходящим индексом начинает после последнего ключа и берёт ограниченную страницу. Нужен устойчивый полный порядок, например created_at,id, и курсор; произвольный номер страницы становится менее удобным.
2. **Когда нужен покрывающий индекс?** Он хранит ключи поиска/сортировки и дополнительные поля через INCLUDE, чтобы запрос мог получать данные из индекса. Обычный индекс часто требует чтения heap для остальных столбцов. Index Only Scan также зависит от visibility map; покрытие увеличивает размер индекса и цену записей. В данной реализации INCLUDE не добавлен без измеренной необходимости.
3. **Какие параметры пула настраиваются и почему?** MaxOpenConns ограничивает параллельные подключения, MaxIdleConns задаёт запас для повторного использования, ConnMaxLifetime и ConnMaxIdleTime ограничивают возраст/простой. Здесь сравниваются 1 и 8 при восьми клиентах; жизненный цикл 30 и 5 минут. Фактические очереди и задержки ещё не измерены.
4. **Что показывает EXPLAIN (ANALYZE, BUFFERS)?** План, реальные строки/циклы/времена выполнения и обращения к буферам. Seq Scan читает таблицу последовательно, Index Scan использует индекс и при необходимости heap; Bitmap Scan может сочетать индекс с пакетным чтением страниц. ANALYZE действительно исполняет запрос, поэтому с изменяющими запросами нужна осторожность. Планы этой практики пока не получены.
5. **Два способа устранить N+1?** Собрать ID и выполнить один ANY/IN-запрос либо загрузить связанные данные JOIN/предзагрузкой подходящей формы. Нужно сохранить порядок, обработку отсутствующих данных и не создавать лишние дубликаты строк. Здесь выбран один батч ANY вместо цикла SELECT.
6. **Когда уместны prepared statements?** Для часто повторяемых параметризованных запросов: можно переиспользовать подготовку и снизить разбор/планирование. Параметры отделены от SQL; значения не вставляются конкатенацией. При неравномерных данных generic plan не всегда выгоден, а statements привязаны к соединениям; эффект нужно измерять. Здесь подготовлены INSERT и SELECT по ID.
7. **Как выбрать размер пула?** Ограничить общую сумму соединений экземпляров сервиса доступной мощностью и лимитом PostgreSQL, провести одинаковую нагрузку для нескольких значений, смотреть RPS, p95/p99, ошибки, WaitCount/WaitDuration, InUse/Idle и нагрузку БД. Большой пул может ухудшить конкуренцию и расход памяти. До замеров выбирать 8 как доказанно лучший нельзя.
