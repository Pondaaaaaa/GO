# Практическое занятие №16 Интеграционное тестирование Notes API

## Цель и результат

Проверить весь путь HTTP → handler → service → repository → реальный PostgreSQL в изолированной среде Docker Compose, вариант A задания. Создан самостоятельный модуль [pz16-integration](https://github.com/Pondaaaaaa/GO/tree/main/practices/pz16-integration). Все обязательные интеграционные проверки выполнены без SKIP; код пока сохранён локально, ссылка станет доступна после пользовательского push. Практики №11–12 не изменены.

## Окружение

Проверка выполнена 13 октября 2026 года на Windows amd64. Go — `go1.27.2 windows/amd64`; Docker Client/Engine — `29.8.2`; Docker Compose — `v5.5.1`; PostgreSQL — `16.6`, образ `postgres:16.6-alpine`. ## Структура и реализация

```text
practices/pz16-integration/
  go.mod, go.sum, README.md
  compose.yaml, run-local.ps1
  cmd/api/main.go
  internal/models/note.go
  internal/db/migrate.go, migrate.sql
  internal/repo/postgres.go
  internal/service/service.go
  internal/httpapi/handlers.go
  integration/notes_test.go
reports/pz16.md
reports/word/pz16.docx
reports/logs/pz16/*.txt
```

HTTP на chi проверяет ID, Content-Type и JSON, запрещает неизвестные поля и лишний JSON, ограничивает тело 1 МиБ. Сервис обрезает пробелы заголовка и проверяет POST/PATCH. Репозиторий выполняет параметризованные запросы через database/sql с pgx и переданным контекстом; SQL ограничен 3 секундами. Пул ограничен четырьмя соединениями. API не раскрывает ошибки драйвера или параметры подключения. Для ID используется strconv.FormatInt, ошибочный фрагмент URL из DOCX не переносился.

Миграция встроена через go:embed и создаёт notes: BIGSERIAL PK, title/content NOT NULL, CHECK непустого title, created_at/updated_at TIMESTAMPTZ. CREATE TABLE IF NOT EXISTS не удаляет существующие данные. При PATCH время обновляется атомарно в SQL:

```sql
UPDATE notes
SET title=COALESCE($2,title), content=COALESCE($3,content),
    updated_at=clock_timestamp()
WHERE id=$1
RETURNING id,title,content,created_at,updated_at;
```

Отдельный триггер не требуется: обновления этого API проходят через репозиторий. Запись SQL вне API не получает автоматическую смену updated_at. Это ограничение явно учитывается.

## Запуск и изоляция

Основная команда из любого каталога PowerShell:

```powershell
& 'D:\MAG\GO\practic\practices\pz16-integration\run-local.ps1'
```

Скрипт подключает setup.ps1, проверяет Docker, создаёт уникальный Compose project, временный пароль и собственный том. Docker сам выделяет loopback-порт. После healthcheck тесты получают временный DSN через окружение процесса. Пароль и DSN не печатаются и не сохраняются в репозитории или отчётных логах; пароль передаётся Docker как переменная окружения одноразового контейнера. Окружение PowerShell восстанавливается в finally, а контейнер и том удаляются. Каждый тест создаёт собственную случайную схему it_<token> и задаёт search_path всем подключениям своего пула. Фикстуры создаются через HTTP POST; t.Cleanup закрывает сервер и пул, удаляет только свою схему. Нет TRUNCATE общих таблиц и зависимости от порядка. Требуются маркер собственного проекта, loopback и тестовая БД notes_test; без параметров тесты получают FAIL, не SKIP.

Последний запуск использовал проект `pz16-a7722b52d5fc40328a5f6d374efcc493`, PostgreSQL был healthy на `127.0.0.1:62596`. Это фактический временный порт, а не настройка для повторного запуска. [docker compose ps](logs/pz16/compose-ps.txt) сохранён при работающем контейнере. После проверок выполнен down --volumes только своего проекта; подтверждено отсутствие его контейнеров и томов. [Лог очистки](logs/pz16/cleanup.txt). Локальный PostgreSQL и чужие контейнеры не использовались.

## Проблемы и ограничения

В начале Engine был остановлен. После запуска Docker Desktop доступ к named pipe был запрещён песочницей; проверки выполнены с разрешённым доступом вне песочницы. В PowerShell 5.1 stderr нативных программ оформлялся как ErrorRecord даже при exit=0: скрипт теперь преобразует строки через ToString и проверяет именно exit code. Окончательная версия скрипта повторно прошла в 5.1, сохранив подлинные логи.

Скриншоты не создавались: DOCX допускает логи, они приложены. Пагинация, фильтрация, CI и testcontainers-go не реализованы: выбран Compose, у списка контракт из №11–12. Выводы о покрытии нагрузкой или конкурентности не делаются. Word создан штатным экспортёром `python scripts/export_reports_docx.py pz16` после окончательной правки Markdown. Сверены текст, семь ответов, таблицы, формат A4, стили и пустые персональные свойства. Отчёт постранично отрисован через LibreOffice и проверен на четырёх страницах: обрезанного текста и нарушенных таблиц нет. [Результат сверки](logs/pz16/report-check.txt).

## Выводы

Интеграционно проверен полный путь от HTTP-запроса до реальной PostgreSQL. Создание, чтение, изменение, удаление и список подтверждены статусами, JSON и отдельными SQL-проверками. Повторная миграция сохраняет данные, а ограничения таблицы запрещают неверный заголовок. Независимые схемы и повтор с перемешанным порядком обеспечили воспроизводимые последовательные прогоны. Скрипт самостоятельно создаёт временную среду и удаляет только принадлежащие ему ресурсы. Дальнейшее улучшение — добавить отдельные сценарии пагинации и фильтрации после расширения контракта API и запуск в CI.

## Контрольные вопросы

1. **Чем интеграционные тесты отличаются от модульных и когда нужны?** Модульный тест проверяет функцию или компонент с подменой зависимостей. Интеграционный проверяет совместную работу слоёв и настоящие SQL-запросы, миграции, ограничения. Unit подходит для быстрых проверок логики; интеграции нужны для обнаружения ошибок на границах HTTP, сервиса и БД.

2. **Зачем Docker при наличии локального PostgreSQL?** Он обеспечивает отдельную версию сервера и одноразовые данные, не затрагивая пользовательские базы. Коллега или CI получает такое же окружение. Требуются Engine и ресурсы для контейнера; первый запуск скачивает образ.

3. **Плюсы и минусы Compose и testcontainers-go?** Compose задаёт инфраструктуру декларативно и легко диагностируется командами ps/logs, но запуск и очистку нужно организовать скриптом или CI. Testcontainers управляет жизненным циклом из Go и удобно выделяет контейнеры тестам, однако добавляет зависимости и инфраструктурный код. Здесь выбран один разрешённый вариант A.

4. **Как обеспечить независимость тестов?** Каждый тест получает собственные данные и схему, создаёт фикстуры и регистрирует cleanup сразу после выделения ресурса. Не опирается на ID или данные другого теста. Транзакционный rollback удобен, если весь проверяемый путь использует ту же транзакцию; HTTP с отдельным пулом требует иной изоляции. В этой работе применены случайные схемы и shuffle.

5. **Как тестировать пагинацию и фильтрацию?** Подготовить фиксированный набор с известным порядком, проверить пустую выборку, совпадения, отсутствие совпадений, границы страниц и неправильные параметры. Сравнить состав и порядок с ожидаемыми ID; убедиться, что страницы не дублируются и не пропускают записи. Отдельно проверить сочетание фильтра и пагинации. Текущий API этих параметров не поддерживает, проверен полный упорядоченный список.

6. **Риски ломающих миграций и безопасная проверка?** DROP, изменение типов и ограничений могут удалить данные, блокировать таблицу или нарушить совместимость кода. Их проверяют на отдельной копии/одноразовой БД с фикстурами, контролируя сохранность данных и повторное применение; для рабочей БД нужны резервное копирование и план перехода. Здесь миграция не содержит разрушения таблиц, очистка ограничена случайной схемой теста.

7. **Как организовать интеграционные тесты в CI?** Выделить job с Docker, поднять уникальный Compose project, дождаться healthcheck, передать временные секреты через окружение и запустить некешированные тесты. Сохранить тестовые логи и состояние контейнера, выполнять очистку даже при ошибке. Доступные CI credentials нельзя печатать; job должен завершаться ошибкой, если тесты пропущены. Конфигурация CI является необязательным дополнением и в этой практике не добавлена.
