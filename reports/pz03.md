# Практическое занятие №3 — HTTP API задач на `net/http`

## Тема и цель

Реализовать HTTP-сервер на стандартной библиотеке Go с хранением задач в памяти, обработкой JSON, фильтрацией, едиными ошибками и middleware-логированием.

## Окружение

- Windows, `windows/amd64`.
- Go: `go version go1.27.2 windows/amd64` (требование — Go 1.21+).
- Git: `git version 2.46.0.windows.1`.
- Go подключён командой `& '.\setup.ps1'` из корня репозитория.
- `8080` занят внешним `httpd`; сервер проверен на свободном `PORT=18083`. Посторонний процесс не останавливался.

## Реализация и структура

Создан отдельный модуль `github.com/Pondaaaaaa/GO/practices/pz03-http`, только на стандартной библиотеке:

- `cmd/server/main.go` — чтение `PORT` (по умолчанию `8080`), запуск и логирование ошибок сервера.
- `internal/api/handlers.go` — `/health`, список и создание задач, фильтр `q`, получение задачи по ID и валидация запросов.
- `internal/api/middleware.go` — логирование метода, пути, фактического HTTP-статуса и длительности. Неявный статус по умолчанию корректно считается `200`.
- `internal/api/responses.go` — общий JSON-ответ и JSON-ошибки с `Content-Type` и заданным статусом.
- `internal/storage/memory.go` — `Task`, возрастающие ID и потокобезопасные `Create`, `Get`, `List` на `sync.RWMutex`.
- `internal/api/handlers_test.go` — тесты создания и валидации, получения/404, а также неявного статуса middleware.
- `dev.ps1` — цели `run`, `build`, `test`; `requests.md` содержит восемь PowerShell-запросов с ожидаемыми статусами.

Ошибку из примера DOCX исправил sentinel-ошибкой `storage.ErrNotFound`. Хранилище возвращает именно этот экземпляр, а обработчик использует `errors.Is(err, storage.ErrNotFound)`. Сравнение через `errors.Is(err, errors.New("not found"))` не работает, потому что каждый вызов `errors.New` создаёт отдельное значение ошибки.

## Проверки

После `& '.\setup.ps1'` в каталоге модуля выполнены `go fmt ./...`, `go vet ./...`, `go test ./...` и `go build ./...`; все команды завершились без ошибок. Также проверены цели `dev.ps1 test` и `dev.ps1 build`. Сервер запущен командой `go run ./cmd/server` с `PORT=18083`; запросы выполнены через `curl.exe --noproxy '*' -i`.

Фактические ответы:

| Запрос | Результат |
| --- | --- |
| `GET /health` | `200 OK`, `Content-Type: application/json`, `{"status":"ok"}` |
| `POST /tasks` с `{"title":"  Buy Milk  "}` | `201 Created`, JSON `{"id":1,"title":"Buy Milk","done":false}` |
| `GET /tasks` | `200 OK`, список с задачей `Buy Milk` |
| `GET /tasks?q=mIlK` | `200 OK`, та же задача; фильтр не зависит от регистра |
| `GET /tasks/1` | `200 OK`, созданная задача |
| `POST /tasks` с `Content-Type: text/plain` | `400 Bad Request`, JSON-ошибка `Content-Type must be application/json` |
| `POST /tasks` с некорректным JSON | `400 Bad Request`, JSON-ошибка `invalid JSON body` |
| `POST /tasks` с пробельным `title` | `400 Bad Request`, JSON-ошибка `title is required` |
| `GET /tasks/not-a-number` | `400 Bad Request`, JSON-ошибка `invalid task id` |
| `GET /tasks/999999` | `404 Not Found`, JSON-ошибка `task not found` |

Ответ health endpoint:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 16

{"status":"ok"}
```

Ответ создания задачи:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Content-Length: 41

{"id":1,"title":"Buy Milk","done":false}
```

Фильтр `GET /tasks?q=mIlK` вернул `200 OK`, `Content-Type: application/json` и:

```json
[{"id":1,"title":"Buy Milk","done":false}]
```

Некорректный тип тела вернул `400 Bad Request`, `Content-Type: application/json` и:

```json
{"error":"Content-Type must be application/json"}
```

Например, ответ `GET /tasks/999999` имел вид:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json
Content-Length: 27

{"error":"task not found"}
```

После этих обращений middleware вывел фактические статусы всех запросов:

```text

2026/10/13 02:20:43 GET /health status=200 duration=0s
2026/10/13 02:20:43 POST /tasks status=201 duration=607.2µs
2026/10/13 02:20:43 GET /tasks status=200 duration=0s
2026/10/13 02:20:43 GET /tasks status=200 duration=0s
2026/10/13 02:20:43 GET /tasks/1 status=200 duration=0s
2026/10/13 02:20:43 POST /tasks status=400 duration=0s
2026/10/13 02:20:43 GET /tasks/not-a-number status=400 duration=0s
2026/10/13 02:20:43 GET /tasks/999999 status=404 duration=0s
2026/10/13 02:20:43 POST /tasks status=400 duration=0s
2026/10/13 02:20:43 POST /tasks status=400 duration=0s
```

Вывод `go test ./...`: пакет API завершился `ok` за `0.563s`; у `cmd/server` и `internal/storage` нет отдельных тестовых файлов. Тесты `httptest.NewRecorder` подтвердили успешное создание с обрезкой пробелов, ошибки неверного `Content-Type`, JSON и пустого заголовка, получение существующей задачи, `400` для неверного ID и `404` для отсутствующей задачи. Отдельный тест подтвердил, что middleware записывает `status=200`, когда обработчик пишет тело без явного `WriteHeader`. Также проверены `dev.ps1 run` и сценарий из `requests.md`: после создания извлечён ID `1`, запрос `GET /tasks/1` вернул `200 OK`.

## Вывод

Сервер, in-memory хранилище, фильтр, единые JSON-ошибки и middleware реализованы; обработка отсутствующей задачи исправлена sentinel-ошибкой. Обязательные проверки и домашнее задание выполнены. Дополнительные PATCH, DELETE, CORS и graceful shutdown не добавлялись.
