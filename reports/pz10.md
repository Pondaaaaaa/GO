## Краткое описание

Разработан отдельный Go-сервис с login и двумя типами HS256 JWT: access на 15 минут и refresh на 7 дней. Пароли двух учебных пользователей хранятся в памяти как bcrypt-хэши; открытые пароли не включаются в ответы. Защищённые запросы используют `Authorization: Bearer <access>`. AuthN проверяет подпись, `exp`, `iat`, `iss`, `aud` и тип токена, затем помещает claims в контекст. AuthZ проверяет роль; правило ABAC разрешает пользователю читать только собственный профиль.

`POST /api/v1/refresh` выдаёт новую пару и помещает идентификатор использованного refresh в потокобезопасный список отзыва до его `exp`. Повторное применение старого refresh получает 401. Этот список хранится только в памяти, что соответствует упрощённому заданию: перезапуск сервера его очищает. Секрет формируется автоматически на время локального прогона и не записывается в репозиторий.

`jwt.go` подписывает access/refresh разными `token_type` и случайными `jti`; валидатор допускает только HS256. В `AuthN` refresh-токен нельзя использовать вместо access. `AuthZRoles("admin")` возвращает 403 для роли user, а `OwnProfileOrAdmin` сравнивает `sub` с `{id}`. ## Окружение и запуск

Проверено на Windows `windows/amd64`, Go `go1.27.2`, PowerShell. Использованы `chi v5.4.0`, `golang-jwt/jwt/v5 v5.3.0`, `golang.org/x/crypto v0.31.0`. PostgreSQL и Docker не требуются.

Одна команда из любого каталога PowerShell:

```powershell
& 'D:\MAG\GO\practic\practices\pz10-auth\run-local.ps1'
```

Скрипт выбирает свободный порт и временный случайный `JWT_SECRET`, запускает сервер, проводит проверки и завершает свой процесс. Для ручного запуска задаются `JWT_SECRET` (минимум 32 байта), необязательные `APP_PORT` (8080), `APP_HOST` (127.0.0.1), `JWT_TTL` (15m), `JWT_REFRESH_TTL` (168h). Команды приведены в [README](../practices/pz10-auth/README.md).

Пример ручных запросов с curl.exe; токен хранится в переменной PowerShell и не печатается:

```powershell
$login = curl.exe --noproxy '*' -sS -X POST http://127.0.0.1:18010/api/v1/login -H 'Content-Type: application/json' -d '{"email":"admin@example.com","password":"secret123"}' | ConvertFrom-Json
$token = $login.access_token
curl.exe --noproxy '*' -i http://127.0.0.1:18010/api/v1/me -H "Authorization: Bearer $token"
curl.exe --noproxy '*' -i http://127.0.0.1:18010/api/v1/admin/stats -H "Authorization: Bearer $token"
$pair = curl.exe --noproxy '*' -sS -X POST http://127.0.0.1:18010/api/v1/refresh -H 'Content-Type: application/json' -d (ConvertTo-Json @{refresh_token=$login.refresh_token} -Compress) | ConvertFrom-Json
```

Для роли user повторите login с `user@example.com`, затем запросите `/api/v1/admin/stats` и `/api/v1/users/1` с её access: оба ответа должны быть 403. При ручном запуске порт должен совпадать с `APP_PORT`; автоматический скрипт передаёт токены сам.

В сценарии старый access остаётся работоспособным до истечения `exp`, поскольку отзывается только refresh.

## Контрольные вопросы

1. **Что такое claims?** Это утверждения в payload JWT. Registered claims имеют стандартные имена, например `sub`, `iat`, `exp`, `iss`, `aud`, `jti`; public claims определяются публичным реестром или пространством имён; private claims согласуются внутри приложения, например `role` и `token_type`. `exp` ограничивает время, в течение которого украденный токен можно использовать.
2. **JWT и серверная сессия.** Подписанный JWT проверяется без поиска сессии в БД, поэтому запросы легче распределять между экземплярами. Но выпущенный access сложно немедленно отозвать без состояния на сервере; сессии проще отзывать, зато хранилище сессий нужно каждому запросу.
3. **Цепочка middleware.** Каждый слой получает запрос и либо передаёт его дальше, либо завершает ответ. AuthN сначала проверяет токен и кладёт claims в контекст. AuthZ затем использует эти claims для решения о доступе; без AuthN ей нечего надёжно проверять.
4. **RBAC и ABAC.** RBAC сравнивает роль с разрешёнными ролями, как `admin` для статистики. ABAC учитывает свойства пользователя и ресурса: владелец с `sub == {id}` может читать свой профиль. ABAC нужен, когда одной роли недостаточно.
5. **Хранение паролей.** Сохраняют медленный парольный хэш bcrypt или Argon2 с уникальной солью, а не быстрый SHA-256. Соль препятствует одинаковым хэшам и готовым таблицам; дополнительный секрет pepper хранится отдельно от базы. В этой работе bcrypt генерирует соль автоматически, pepper не применяется.

## Ограничения и вывод

Обязательные JWT, AuthN/AuthZ, refresh и ABAC реализованы и проверены. Из необязательных заданий выполнены единый JSON ошибок и логирование статуса/времени. RS256 с ротацией ключей и rate limit не реализовывались. Для публичного сервиса потребуются HTTPS, постоянное хранилище отзыва refresh, защищённое хранение ключа и ограничение частоты login.
