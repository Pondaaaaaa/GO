# Практическое занятие №9 — регистрация и вход с bcrypt

## Цель и окружение

Реализовать `POST /auth/register` и `POST /auth/login` на Go с хранением только bcrypt-хэша пароля в PostgreSQL. Подготовить модель пользователя к следующей практике с JWT, не выдавая токен в этой работе.

Фактическая проверка выполнена на Windows `windows/amd64`, Go `go1.27.2`, PostgreSQL/`psql` `18.6`, Windows PowerShell 5.1. Для проверки использовался отдельный временный кластер PostgreSQL с кодировкой UTF-8; рабочие базы пользователя не менялись. Модуль использует `chi v5.4.0`, `gorm v1.31.2`, `gorm.io/driver/postgres v1.6.3`, `golang.org/x/crypto v0.31.0`.

## Проект и выполненная работа

Модуль расположен в `practices/pz09-auth/`. Структура:

```text
cmd/api/main.go                         запуск chi, маршруты, AutoMigrate
internal/core/user.go                  модель User
internal/repo/user_repo.go             подключение, миграция, Create/ByEmail
internal/http/handlers/auth.go         Register, Login, валидация, bcrypt
internal/http/handlers/auth_test.go    проверки ответов и отсутствия утечки
internal/platform/config/config.go     DB_DSN, BCRYPT_COST, APP_ADDR
run-local.ps1                           настройка, запуск и проверка
```

В модели есть `ID`, уникальный `Email`, `PasswordHash`, `CreatedAt` и `UpdatedAt`. Поле `PasswordHash` имеет `json:"-"`, а ответы дополнительно собираются из разрешённых полей `id` и `email`. Таблица создаётся `AutoMigrate(&core.User{})`; результат проверен настоящим запросом к `information_schema.columns`. Для корректной обработки повторного email включён `TranslateError: true`: ошибка уникальности преобразуется в 409.

Регистрация приводит email к нижнему регистру, проверяет адрес и длину пароля от 8 до 72 байт. В `Register` пароль преобразуется до записи в БД:

```go
hash, err := bcrypt.GenerateFromPassword([]byte(in.Password), h.BcryptCost)
user := core.User{Email: in.Email, PasswordHash: string(hash)}
err = h.Users.Create(r.Context(), &user)
```

`Login` ищет пользователя по нормализованному email и сравнивает пароль со встроенной солью хэша. Для неверного пароля и неизвестного email возвращает один ответ `401 {"error":"invalid_credentials"}`:

```go
user, err := h.Users.ByEmail(r.Context(), in.Email)
if bcrypt.CompareHashAndPassword([]byte(user.PasswordHash), []byte(in.Password)) != nil {
    writeJSON(w, http.StatusUnauthorized, map[string]string{"error": "invalid_credentials"})
    return
}
```

Полные обработчики: [Register и Login](../practices/pz09-auth/internal/http/handlers/auth.go). Отдельно проверены ошибочный JSON, слишком короткий пароль, неверный email и запрет дополнительных полей. Сервер не записывает тела HTTP-запросов в лог. Ограничение частоты входа и HTTPS отмечены как необходимые для публичного сервиса, но не относятся к локальному учебному запуску.

```powershell

Шаблон ручной настройки приведён в [README](../practices/pz09-auth/README.md); реальные пароли не публикуются.

## Контрольные вопросы

1. **Зачем хранить хэш вместо пароля и зачем соль?** Хэш позволяет проверить введённый пароль, не сохраняя исходную строку. Уникальная случайная соль даёт разные хэши даже для одинаковых паролей и мешает использовать готовые таблицы совпадений.
2. **Почему bcrypt, а не SHA-256; что делает cost?** SHA-256 рассчитан на быстрое вычисление, что облегчает массовый подбор. bcrypt медленный, содержит соль и настраиваемую стоимость. Повышение cost замедляет и легитимный вход, и перебор; снижение ускоряет оба. Значение подбирают по времени на целевой машине; в этой работе по заданию использовано 12. Тесты используют минимальную стоимость ради скорости, не для реального сервиса.
3. **Какие статусы возвращают маршруты?** Регистрация: 201 при создании, 409 при занятом email, 400 при неверном вводе. Вход: 200 при верной паре, 401 при неверной, 400 при неправильном JSON или пустых полях. Внутренняя ошибка БД даёт 500 без деталей.
4. **Чем опасны подробные ошибки входа?** Ответ «email существует, пароль неверный» позволяет перечислять зарегистрированные адреса. Одинаковый `invalid_credentials` не раскрывает существование аккаунта.
5. **Почему нет токена?** В №9 отрабатываются хранение и проверка пароля. В №10 успешный вход дополнится выдачей JWT для последующей аутентификации запросов.

## Проблемы и вывод

Временный PostgreSQL сначала создался в кодировке WIN1251, несовместимой с используемым драйвером для части миграции. Проверка повторена на отдельном кластере UTF-8 и прошла. Также Windows PowerShell 5.1 не сохранил тело ответа HTTP 409 при `Invoke-WebRequest`; автоматический сценарий исправлен на `HttpClient` и повторно выполнен. Получены все четыре основных статуса, миграция и bcrypt-хранение подтверждены. Для окончательного оформления остаются настоящие скриншоты.
