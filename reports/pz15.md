# Практическое занятие 15 Unit тестирование Go

## Цель и выполненная работа

Создан отдельный Go-модуль с unit-тестами арифметики, обрезки строки и поиска ID через интерфейс репозитория. Проверены результаты, ошибки, граничные случаи и взаимодействие с локальным stub. Все обязательные команды выполнены, покрытие каждого из трёх пакетов составляет 100,0%. Тестам не требуются БД, сеть или сервер; существующие практики не изменялись.

Репозиторий: [Pondaaaaaa/GO](https://github.com/Pondaaaaaa/GO). Код после пользовательского push будет доступен по [practices/pz15-tests](https://github.com/Pondaaaaaa/GO/tree/main/practices/pz15-tests). На момент подготовки отчёта выполнен только локальный коммит, удалённая публикация не проверялась. [Локальный README](../practices/pz15-tests/README.md).

## Проверенные сценарии

`TestSum_Table` использует стандартный testing и шесть именованных t.Run: положительные числа, разные знаки, два отрицательных числа, два нуля, нулевой операнд и взаимное сокращение. Каждый результат сравнивается с заданным want через t.Errorf; простого вызова без проверки нет.

`TestDivide_OkAndError` содержит восемь кейсов: точное деление, остаток, отрицательный числитель, отрицательный знаменатель, два отрицательных операнда, нулевой числитель, деление на ноль и 0/0. require.NoError проверяет предусловие успешного ответа, require.Error — наличие ошибки, assert.EqualError — текст divide by zero. assert.Equal проверяет число и в успешных, и в ошибочных случаях. Деление целочисленное, с усечением к нулю: -7/3 даёт -2.

`TestClip` проверяет пустую строку с положительным/нулевым/отрицательным max, непустую строку при max=0 и max<0, равную и большую длину, обрезку и первый байт. Дополнительно проверены UTF-8 на целой границе и внутри символа. Всего 12 именованных подтестов. Контракт специально **считает длину и обрезку по байтам**: для Clip("П",1) ожидается строка из байта 0xD0, и utf8.ValidString возвращает false. Это ограничение функции, а не исправленный Unicode-алгоритм.

`TestService_FindIDByEmail` использует локальный stub, реализующий UserRepo.ByEmail. Пять случаев: найден ID 42, отсутствующий email, пустой email, ошибка репозитория и обёрнутый ErrNotFound. assert.ErrorIs проверяет sentinel, включая цепочку `%w`; assert.Same проверяет возврат исходной ошибки репозитория без замены. Даже если stub возвращает User с ID 999 вместе с ошибкой, сервис обязан вернуть ID 0 — это проверяется. Каждый кейс также проверяет передачу точного email одним вызовом. Stub создаётся заново в каждом t.Run и не зависит от других тестов.

Ключевой фрагмент проверки сервиса:

```go
id, err := svc.FindIDByEmail(tc.email)
if tc.wantErr != nil {
    require.Error(t, err)
    assert.ErrorIs(t, err, tc.wantErr)
} else {
    require.NoError(t, err)
}
assert.Equal(t, tc.wantID, id)
assert.Equal(t, []string{tc.email}, repo.calls)
```

Итого выполнены четыре основных Test-функции и 31 именованный подтест. В каждой проверяется ожидаемое поведение; покрытие не набирается бессодержательными вызовами.

## Проблемы и ограничения

Первоначальная загрузка отсутствующих зависимостей и покрытие столкнулись с ограничениями песочницы: сеть была недоступна, а сборщик покрытия получил Access is denied при переименовании метаданных. После разрешённого запуска вне песочницы зависимости загрузились и покрытие успешно получено. Для команды cover вариант с незаключёнными в кавычки аргументами завершился ошибкой too many arguments; проверенный вариант с кавычками и `-o=...` включён в README.

Clip может возвращать невалидный UTF-8, потому что работает по байтам. Арифметика использует машинный int без отдельного контроля переполнения; Divide не вычисляет дробный результат. Сервис не нормализует email и требует предоставленный репозиторий. Реальную интеграцию с БД эти unit-тесты не проверяют. Необязательные BenchmarkSum, тест паники и CI workflow не добавлялись.

## Контрольные вопросы

1. **Unit и интеграционный тест, зачем изоляция?** Unit проверяет отдельную функцию или метод с контролируемыми зависимостями; интеграционный тест проверяет взаимодействие реальных компонентов, например сервиса и БД. Изоляция делает тест быстрым, повторяемым и независимым от сети, времени и внешних данных. Здесь сервис тестируется со stub в памяти.
2. **Табличные тесты и когда они полезны?** Кейсы хранятся в срезе структур с именем, входом, ожидаемым результатом и ошибкой; цикл запускает t.Run для каждого. Это удобно для одинаковой логики с несколькими значениями и граничными случаями. Именованные подтесты показывают, какой вход сломался, и позволяют выбирать его через -run.
3. **Что даёт testify и когда достаточно testing?** testify сокращает проверки равенства, наличия ошибок и errors.Is-совместимости, улучшая сообщения. assert продолжает текущий тест после неудачи; require прекращает текущий тест/подтест, если дальнейшая проверка бессмысленна. Для простого сравнения Sum достаточно t.Errorf; для успеха перед разбором результата уместен require.NoError.
4. **Что показывает go test -cover и почему процент не равен качеству?** Он показывает долю выполненных инструментированных statements. Высокое покрытие не проверяет само по себе значения и не гарантирует все сочетания входов: тест без assertions тоже может выполнить код. Поэтому здесь результаты и ошибки проверяются явно, а граничные и отрицательные кейсы описаны отдельно.
5. **Как проверять ошибки и негативные случаи?** Для успеха проверять отсутствие ошибки и значение; для отказа — наличие ошибки, её тип/sentinel через ErrorIs и контракт результата. Хорошие примеры: Divide(10,0) возвращает 0 и divide by zero, отсутствующий пользователь — 0 и ErrNotFound, ошибка хранилища передаётся без подмены. Сравнение только текста недостаточно для обёрнутых ошибок.
6. **Как интерфейсы и стабы/моки позволяют обходиться без БД?** Сервис зависит от контракта UserRepo, а тест передаёт локальную реализацию. Stub возвращает заранее выбранные User/ошибки; mock дополнительно проверяет взаимодействия. В данной работе stub также записывает вызовы, позволяя проверить точный аргумент и один вызов, а реальная БД не используется.

## Итоговые выводы

Табличные unit-тесты проверили арифметику, байтовую обрезку и поиск ID через изолированный репозиторий. Успешные и ошибочные ветви проверены по возвращаемым значениям, а не только выполнены ради покрытия. Особое внимание потребовалось различию assert/require, сохранению ошибки репозитория и разрезанию UTF-8 в Clip. Каждый целевой пакет достиг 100,0% statements, при этом ограничения входов и отсутствие интеграционных проверок остаются явно описанными.
